# Codex — очередь минимальных задач для INVARIANT

**Статус:** план задач. Ничего отсюда не запускается автоматически. Репозиторий: `Nozomit01/Invariant`. Ветка документации: `docs/codex-v4-review`.

**Главное условие:** **не начинать программирование** до отдельного подтверждения автором контрольной точки 0 (Gate 0). До утверждения финального имени, разрешения/масштабирования, объёма демо и формата проверки можно выполнять только аналитические задачи. Канон: `docs/canon/`, изменения: `docs/production/DECISIONS_2026-10-19.md`.

## Защита бюджета Codex — применять к каждой задаче

1. Давать Codex одну задачу за раз, максимум одну узкую цель и исчерпывающий список допустимых файлов. Никаких параллельных агентов и спонтанных «улучшений».
2. Сначала просить **только план и перечень файлов**, без коммитов и исполнения, если объём неясен. Начинать работу после согласования.
3. **Не устанавливать зависимости**, не запускать длительные сборки, бесконечные циклы исправлений, внешние платные инструменты или автоматические дополнительные задачи без согласия.
4. Максимум **одна итерация исправления** в рамках задачи; если тест не проходит — остановиться, приложить ошибку и запросить следующее действие.
5. Отчёт: изменённые файлы, что проверить, реальные результаты команд, отклонения от плана, риски. **Не обещать точный расход кредитов**: он зависит от выбранного режима, окружения и объёма фактической работы.
6. Одна задача → один небольшой PR, в идеале без затрагивания других модулей и без изменений художественного канона.

## Этап 0 — документы / без кода

### D0 — инвентаризация и контроль противоречий

**Вход:** GDD v0.2, Character Bible v1, `AGENTS.md`, решение 19.10.2026, `DEMO_SCOPE.md`.

**Разрешено:** чтение, отчёт и таблица блокирующих решений. **Запрещено:** любые изменения `.gd`, `.tscn`, `project.godot`, игровые ассеты и CI.

**Готово, когда:** нет выдуманных диалогов/секретов; названы только действительно блокирующие решения; установлено, что демо содержит «Прыжок», «Уход», полный хаб и отдельный экран завершения после двух разных исходов с последующим возвращением в хаб. Ходьба по улице в обычном хабе **отсутствует** по GDD §17.

### D1 — технические договорённости перед первым коммитом кода

**Выход:** краткая спецификация: версия Godot 4.x stable, разрешение 4:3 и масштабирование, схема ввода для Windows, способ тестировать Godot без локального ПК. Это предложения на утверждение автору, а не лицензия начать писать код.

**Готово, когда:** все обязательные параметры подтверждены автором либо помечены `BLOCKED_BY_DECISION`.

## Этап 1 — реализация только после письменного Gate 0

### G1 — минимальный Godot-проект

**Файлы:** `project.godot`, один стартовый экран, базовая настройка ввода и краткая инструкция по запуску. Без сюжетных сцен, систем диалога, сохранений и Steamworks.

**Приёмка:** проект открывается в согласованной версии Godot, стартовая сцена запускается; есть лог реально выполненной проверки. При недоступном Godot прямо написать «не тестировалось», без фантазий об успехе.

### G2 — крыша и игрок

**Файлы:** одна тестовая 2D-сцена крыши и скрипт движения/взаимодействия. Заглушки помечать `PLACEHOLDER_NON_CANON`.

**Приёмка:** можно перемещаться, осматриваться и взаимодействовать с заданной точкой; никаких новых художественных решений и катсцен.

### G3 — минимальный диалог со свободой действий

**Файлы:** локальная модель диалога, UI реплик/выборов и проверочная сцена. Нельзя автоматически блокировать передвижение во время большинства диалогов. Сценарный текст-заглушка — явно неканонический.

**Приёмка:** выбор, молчание и уход — различимые действия; нет жёстко встроенного нового сюжета.

### G4 — скрытые состояния и события одного цикла

**Файлы:** состояние текущего прохождения и небольшой обработчик событий. Использовать направления из GDD: тревога, злость, скука, апатия, без видимых чисел и без «универсальной правильной формулы».

**Приёмка:** на тестовых переходах состояния и реакции воспроизводимы, причины изменений проверяемы в отладочном отчёте.

### G5 — одна проверочная развязка → переход в хаб

**Файлы:** минимальная связка одной существующей ветки и пустого хаба. Временная заглушка допустима лишь для проверки связности, **не заменяет утверждённый полный хаб релизной демоверсии**.

**Приёмка:** крыша → диалог/состояние → исход → хаб, без аварии и без потери управления.

### G6 — полноценный хаб §17–18

**Файлы:** отдельные небольшие изменения: (а) улица/герой/сигарета/переход на крышу; (б) физический плеер из сумки; (в) доступные «Воспоминания»/музыка и наклейки. Разбить по необходимости на отдельные PR.

**Приёмка:** в обычном хабе **нет свободной ходьбы**; можно осматривать окружение и пользоваться плеером; следующий цикл запускается естественным действием; за каждую из двух концовок есть по наклейке; номера концовок на экране отсутствуют.

### G7 — сохранения и ограничение контента демо

**Файлы:** сохранение известных исходов, наклеек и доступных воспоминаний, сериализация/загрузка, проверка повторного прохождения.

**Приёмка:** состояние переживает перезапуск; экран завершения демоверсии срабатывает по двум **разным** исходам, не по двум повторениям одного.

### G8 — экран завершения демо

**Файлы:** экран с текстом «Демоверсия завершена» / ожиданием полного релиза (окончательный текст утверждает автор); переход обратно в **полноценный** хаб и неограниченное продолжение циклов.

**Приёмка:** игра не закрывается, не удаляет прогресс, не показывает True Ending, после экрана можно вновь получить оба доступных исхода; экран не возникает при повторных прохождениях без новой авторской настройки.

### G9 — Windows-сборка, проверки, ассеты

**Файлы:** GitHub Actions, экспортные шаблоны и проверка только после отдельной задачи. Аудио и спрайты подгружаются лишь из реально доступных и разрешённых к распространению материалов.

**Приёмка:** CI показывает фактический результат; артефакт `.exe` действительно создан, если экспорт утверждён; запуск на настоящем Windows-ПК проверяется отдельно.

## Дисциплина работы

После каждого пункта сверять с `AGENTS.md`, GDD и `ROADMAP.md`. Не переходить к следующему пункту автоматически. Игра не должна превращаться в набор пустых систем вместо одного целостного цикла.
