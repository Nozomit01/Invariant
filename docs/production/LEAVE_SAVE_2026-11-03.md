# Сохранение подтверждённого «Ухода» — план и решения

База: `6c0f5d9a3f9b3e49f66d7ac49ad3d790556372fb` (745 PASS), отдельная ветка
`codex/leave-outcome-save`. Поручение разрешает реализацию без нового согласования
технических решений. Канон, графика, main, PR и APK не затрагиваются.

## Основание и границы

GDD §26 требует хранить просмотренные обычные исходы; §18 и §19.2 объединяют
варианты и повторения «Ухода» в один результат. Сохраняется `leave`, не departure_id,
не технические стадии, не факт открытия хаба. Завершение нынешнего технического
представления подтверждает игровой исход; пометка о временной постановке остаётся
в журнале сессии. Сохранение не делает художественную концовку готовой.
Наклейки, другие исходы, продолжение незавершённого прохода и Steam не добавляются.

## Решение

Один перезаписываемый JSON прост, но может повредить старую копию. Схема backup
требует менять существующие файлы. Выбран маленький журнал неизменяемых подтверждений
в `user://outcomes_v1`: запись в новой зарезервированной директории, flush/close,
проверка, затем rename из pending в confirmed. Загрузка учитывает только полностью
проверенный confirmed; незавершённый pending игнорируется. Повторы объединяются
по идентификатору исхода и не создают новых записей, когда есть исправная запись.
Повреждённые, неизвестные и посторонние файлы не удаляются и не перезаписываются.

## Особое внимание при проверке

Неизвестная версия/исход не выдаёт награду; недописанный файл не выдаёт награду;
запрет записи не ломает игровой цикл; повтор не размножает достижения;
старые повреждённые и посторонние файлы остаются побайтно прежними.
Flush/rename не являются обещанием выживания при физическом отказе накопителя.

## Реализованное поведение

Формат одной записи: `{"version":1,"outcome":"leave","completed":true}`.
Хранилище — `user://outcomes_v1/receipt-<случайный ID>/confirmed.json`.
Новая директория резервируется make_dir (коллизия не перезаписывает чужую).
В неё пишется record.pending; flush/close и повторная валидация предшествуют rename.
Ни один старый файл не является целью записи, rename или удаления.
Неверный JSON, версия, тип полей, неизвестный исход, pending и символьные ссылки
на receipt/confirmed игнорируются. На чтение одной записи установлен предел 4 КБ.

`SessionOutcomes.completed_outcomes()` лениво восстанавливает один `leave` с диска;
журнал событий с departure_id при запуске пуст. Единственный production-вызов записи
расположен после проверки завершения в complete_leave. Прямое открытие хаба не пишет
исход. Ошибка записи остаётся в last_save_error, фактический результат остаётся
в памяти до закрытия процесса; хаб показывает «Не удалось сохранить прогресс».
Следующий действительно завершённый уход снова пытается сохранить результат.
После полного повреждения всех записей исход не придумывается: новый завершённый
проход создаёт исправную запись рядом с повреждёнными.

## Ограничения

Проверка проводилась headless в Linux; реальный Android/Windows и визуальное
отображение сообщения на устройстве не проверялись. Перекрытие проверено по
реальным размерам Control/Label в Godot. APK и экспорт не запускались.
Нет испытания отключением питания, настоящим заполнением диска или отказом rename;
ошибка записи воспроизведена файлом, препятствующим созданию каталога.
Нет миграции неизвестных будущих форматов или восстановления полностью испорченных
данных. Повреждённые файлы сохраняются для последующего разбора, автоматической
очистки нет. Наклейка и UI просмотра сохранённого прогресса в этот шаг не входят.

### Уточнение по независимому статическому обзору

Два одновременно запущенных процесса при первом сохранении могут оба увидеть
отсутствие результата и создать две разные физические записи. Чтение объединяет
их в один логический `leave`; они не становятся двумя разными достижениями.
Межпроцессные проверки этой итерации последовательные: конкурентный первый
commit не воспроизводился. Межпроцессной блокировки, гарантирующей ровно один
физический файл, нет. Это ограничение, не подтверждённая ошибка игрового прогресса.
Надёжность при потере питания и отказе rename остаётся непроверенной.
По поручению автора код сохранения после этого обзора не изменён.
